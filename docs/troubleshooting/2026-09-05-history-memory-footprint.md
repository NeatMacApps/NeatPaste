# 历史常驻内存偏高（2026-09-05）

## 症状触发词

活动监视器里 NeatPaste 占一百多兆、内存比想象中大、物理占用峰值突然冲到几百兆、Application Support 里 `history.json` 很大、复制几张截图后内存明显涨。

## 本机实测口径（可复现）

在已安装的应用上（本记录对应 v1.0.4）：

| 口径 | 量级 | 说明 |
|---|---|---|
| 系统 Memory footprint | ~100 MB | `footprint -p <pid>` / `vmmap` 的 Physical footprint，更接近「真实占住」 |
| 活动监视器常看的 RSS | ~160 MB | 含可回收页，数字会偏高 |
| 进程峰值 footprint | 可到 ~600 MB | 读写超大 `history.json` 编解码时会出现，不是稳态 |
| 本机历史文件 | `~/Library/Application Support/NeatPaste/history.json` | 体积与稳态 footprint 同量级时，优先怀疑「整包进内存」而不是泄漏 |

堆里大头通常是 Foundation 的数据块（剪贴板原始字节），不是界面。

## 根因（已核实）

1. **7 天历史整包常驻内存。** 持久化是单文件 JSON；启动时整文件解码进内存列表，之后每条的全部格式字节都挂在内存里。契约要求重启后仍在、且不把富文本/图片降成纯文本，所以会存完整载荷。
2. **体积几乎全是图片，且同一图存了多套格式。** 文本条数再多也只占很小一块。系统复制图片时往往同时带 TIFF / PNG / JPEG 等；旧名与 `public.*` 名还会各存一份几乎相同的 TIFF（或 PNG）。实测：去掉同图别名重复后体积大约减半；若每条图片只留一种优先格式，可再降一个数量级。HTML 等富文本在本机样本里占比很小。
3. **峰值尖刺来自整文件 JSON + Base64。** 二进制载荷进 JSON 会胀大约三分之一；编解码时还会再有一份临时缓冲，所以峰值可以远高于稳态。

这不是典型泄漏：关机前 footprint 与历史文件体量同向；条目少、几乎无图时占用会明显更低。

## 改 / 排查时禁止的误修

- **不要为了省内存改成「只保留纯文本」。** 产品契约明确禁止把富文本/图片降级。
- **不要为了省内存拿掉本机持久化、改成只活在本次进程。** 契约要求重启后 7 天历史仍在。
- **不要把活动监视器 RSS 当成唯一真相，也不要用峰值尖刺断言泄漏。** 先看 footprint，再看 `history.json` 体积与带图条目。
- **不要引入 SwiftData / Core Data / GRDB 当「顺便换存储」。** 工程约束已钉死文件持久化接口。

## 若要压占用（方向，未在本记录落地）

在仍满足「不降级、重启仍在、粘贴可写回原格式」的前提下，可考虑（需单独设计与验收）：

- 收录时对**同图多别名**去重（旧名与 `public.*` 只留一份）。
- 每条图片只持久化一种优先格式（如 PNG/JPEG），粘贴时再派生；须确认写回目标应用是否仍满意。
- 大图落独立文件、列表只留元数据与缩略图，按需读原图；持久化仍走本机文件，不换数据库栈。
- 编解码大历史时避免峰值叠峰（流式/分片写、写盘与内存列表解耦）。

## 验收时怎么量

1. 记当前 `history.json` 体积与条目数（可用脚本统计带图条数、各格式体积）。
2. 冷启动后等几十秒，取 `footprint -p $(pgrep -x NeatPaste)`，不要只看 RSS。
3. 复制一张大图、再打开面板粘贴一次，看稳态是否回到与文件体量同量级，峰值是否只在读写瞬间出现。
